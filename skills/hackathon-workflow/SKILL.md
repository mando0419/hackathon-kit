# 해커톤 과제 진행 절차

이 스킬은 과제 지시문과 제공 데이터를 받은 직후부터 제출까지의 순서를 정한다. 과제 내용 자체(정답, 알고리즘)는 담고 있지 않다.

## 0–20분: 해부와 확인
1. 지시문을 문장 단위로 표로 정리한다: [번호 | 원문 | 분류(명시/암묵/제약/평가단서) | 애매한 점].
2. 제공 데이터를 탐색한다: 파일별 행 수, 열, 결측, 파일 간 ID 불일치, 지시문과 다른 값. 결과는 표로.
3. 애매한 점과 데이터 불일치 중 구조에 영향이 큰 것 3–5개를 담당자 질문 후보로 정리한다. 질문은 "~로 하려고 합니다. 맞을까요?" 형식으로 쓴다.
4. 코드는 쓰지 않는다.

## 20–35분: 계획
1. PLAN.md: 요구사항 번호, 담당자 답변 원문, 가정, 안 만들 것, 마일스톤(세로로 자르기), 각 마일스톤의 완료 기준과 테스트.
2. ARCHITECTURE.md: 폴더별 역할, 대표 흐름 하나, 서버가 최종 권한을 갖는 것.
3. 첫 커밋.

## 35–140분: 마일스톤 반복
- M1 뼈대: 서버 + DB + 헬스체크 + 환경변수 + (역할이 있으면) 로그인 + Dockerfile.
- 이후 마일스톤마다: 테스트 먼저 → 구현 → 테스트 통과 → 화면 확인 → 커밋 → HANDOFF.md, ARCHITECTURE.md 갱신.
- 내보내기·검증용 출력이 있으면 그 출력이 규칙을 지키는지 검사하는 테스트(규칙 검사기)를 만든다.
- 계획보다 15분 이상 늦으면 다음 마일스톤 범위를 줄인다.

## 140–160분: 대조와 점검
1. 요구사항 대조표: [번호 | 요구사항 | 구현/부분/없음 | 근거 파일:함수 | 확인 방법]. 코드는 고치지 않는다.
2. 부분/없음 중 중요한 2개만 고친다. 나머지는 HOW_TO_RUN.md "가정과 제한 사항"에 적는다.
3. `bash scripts/preflight.sh --docker`로 제출 점검을 돌린다 (이 저장소를 /tmp/kit에 받았다면 `bash /tmp/kit/scripts/preflight.sh --docker`).

## 160–170분: 문서와 제출
- HOW_TO_RUN.md를 지시문 양식대로 채우고, 적힌 명령으로 실제로 켜지는지 확인한다.
- AI_COLLABORATION.md는 사용자가 직접 쓴다. AI는 근거 자료(커밋, 테스트 이름, 버그 사례)만 목록으로 정리해 준다.
- git status가 깨끗한지 확인하고 최종 커밋. 마감 10분 전 제출.

## 하지 않을 것
- 남은 시간에 완료 기준 없는 "꾸미기"를 하지 않는다.
- 제공 파일을 수정하지 않는다.
- 비밀 값을 코드나 .env.example에 넣지 않는다.
